3. Enter application/client ID and a newly managed client secret in Firebase Authentication's Microsoft (`microsoft.com`) provider configuration. Record expiry/rotation and owner. 4. Configure the Entra ID-token optional claim `acct` where supported so the backend can distinguish member (`0`) from guest accounts; missing/guest claims fail closed. ## Email proof and secret handling

The dormant TLS SMTP adapter demonstrates integration with an existing corporate mail service; that service's owner must approve sender, authentication policy, outbound access, delivery/abuse limits and retention. Local fallback material is guarded to demo/emulator mode and never a production default. Do not put any such value in `.env.example`, frontend variables or Actions logs. No code/SIN appears in email except the separate authentication code; never email submission content.

## Role bootstrap and contractor list

After approved deployment only, a trusted operator should create `roles/{firebaseUid}` in the explicit named portal database using scoped administration. The schema is `{active,tenantId,objectId,invitationManagement,statusViewing,correctionManagement,sensitiveRetrieval}`. Bind it to a verified MI member, with minimum necessary flags; no client may create/change roles. Do not copy privileges from another app or grant by domain. Even `sensitiveRetrieval:true` cannot enable this build's blocked reveal endpoint. Revoking the role blocks subsequent calls and the dashboard's own-role listener clears the interface.

Use [the synthetic example](../examples/approved-contractors.example.csv) for local imports. Actual contractor emails must be supplied through the approved dashboard after authorization, never committed to the repo. Emails are primary access-list values; names are optional, status is active/revoked/removed. Reimport/removal never clears consumed invitation slots. A correction request revokes access; new-submission/reissue after approved disposal is deliberately pending review rather than an administrator shortcut.
